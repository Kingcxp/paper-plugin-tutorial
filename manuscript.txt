相信在座的各位都玩过 Minecraft，甚至开过服，对吧？当我们不满足于原版生存，想要给服务器加点 RPG 元素、经济系统或者一些奇奇怪怪的玩法时，‘插件’就是我们的一件强而有力的武器。今天，我将带大家从零开始，逐步了解服务器插件是如何开发的，以及它能够做到什么。

在正式开始写代码之前，我们需要搞清楚一个基础问题：我们到底是在什么服务端上写代码？
大家来看这张历史演进图：
最开始是 Vanilla 香草服务器，也就是 Mojang 官方的原版服务端，它是原汁原味的，但最大的问题是——它就像一块铁板，无法加载任何插件。
后来社区的大神们逆向了服务端的代码，搞出了 CraftBukkit，这是第一个广泛被使用的插件服务端，它定义了最初的 Bukkit API，也就是我们今天写插件的基础。
再后来，因为 CraftBukkit 性能不够，社区又分叉出了 Spigot，提供了更好的性能和更多的 API。
而之后，出现了 Paper！它站在了 Spigot 的肩膀上，针对多线程、区块加载做了不少的性能优化，而且它的 API 极其好用。
当然，现在还有像 Purpur 这样的服务端，它其实就是基于 Paper 再次包装，提供了更加强劲的性能。我们今天的开发，就是基于现代的 Paper 平台提供的方便的服务器 API。

很多人会问：我要改游戏，为什么非得写插件？写 Mod 不行吗？写数据包 (Datapack) 不香吗？
我们分别从‘编写难度、安装难度、使用效果’这三个维度来对比一下：
编写难度指的是当我们在完全零基础的情况下，想要实现一个功能，到底有多困难？
安装难度指的是玩家在使用我们编写好的功能时，需要花费怎样的努力？
使用效果指的是我们使用的这个框架能否支持我们实现足够多的，想要的功能？

首先是数据包：
在编写难度上，因为数据包相当于是 Mojang 官方提供的对于原版内容的扩展，所以它对于原版内容的修改非常的快速便捷，但当它遇到一些更加复杂的逻辑时，就只能依赖计分板、实体等绕路的方法来解决问题，在很多情况下非常折磨人。我一写数据包的哥们就跟我说，数据包是挺好用的，但是写起来很痛苦。
在安装难度上，因为数据包是直接内置在游戏存档中的，无论是在服务端还是在客户端都是下载一个地图的问题，完全不需要经过任何额外操作，还是非常方便的。
在使用效果上，因为数据包是依托原版计算机制的，因此它只能遵守服务器的 tick 更新模式，在主线程上运行，也只能修改游戏中的内容，没有办法对服务器所在的本地文件或远程网络上的内容进行修改，当遇到一些需要大量计算的内容是更是会严重拖垮服务器计算资源，造成严重的卡顿和回弹。

然后是模组：
在编写难度上，模组可以对一些游戏的底层进行了一些修改，比如自定义渲染、自定义物品方块等，因此编写难度会比较高，虽然没有这上面说的这么夸张，但确实会需要学会很多东西才可以畅快编写。
在安装难度上，玩家需要自行安装合适的模组加载器，然后将所有的模组安装上去，解决版本适配问题，解决模组之间的冲突问题，解决一大堆运行时遇到的问题，需要一定的计算机基础，然后才能正常运行。当然，你也可以选择现代化的启动器一键安装对吧？但这仍然会带来不小的安装门槛，会劝退不少第一次想玩模组，但不太会折腾电脑的玩家。
在使用效果上，模组自然是当之无愧的无所不能，无论是修改游戏内容，还是修改服务器行为，还是修改游戏底层，都可以做到。

最后是我们今天要说到的插件：
在编写难度上，插件是依托于服务端 API 的，因此编写难度会低很多，基本上只要会写代码，都不一定要会 Java，然后知道一些面向对象、线程和计算机网络的基础常识，就可以轻松上手。听起来好像很夸张，但是真的很基础！学过一些编程语言的同学们基本上都能比较轻松的应对和上手！
在安装难度上，插件是依托于服务端运行的，玩家只需要连接到服务器进行游玩就可以了，需要安装插件？那不是我们的事儿，那是腐竹的事！让腐竹操心去！压榨腐竹！
在使用效果上，和数据包一样，插件也是主要对原版机制进行修改，不过除了插件能做到的内容之外，因为插件开发是依托 Java 平台的，因此 Java 语言本身能提供的不少功能，如多线程运算、网络交互、文件操作等，甚至加载并调用外部的 jar 包，都可以轻松实现，因此插件可以做到的内容，也非常多！唯一遗憾的是比较难注入自定义的物品和模型，只能使用和数据包类似的取巧的办法。

所以为什么我们要选择服务器插件呢？
首先，开发难度适中，对吧？我们不需要掌握非常复杂的底层技术，只需要掌握一些基础知识，以及会查文档就可以了。
其次，因为安装压力完全给到我们可怜的腐竹对吧？对于想要玩到我们制作的内容的玩家只需要下载一个原版客户端，当然要是对应版本的，然后就能无缝加入服务器，非常方便，非常的好用啊！
最后，相较于同样安装极其方便的数据包，插件显然有更多的可能性，可以做到更多的事情，而且性能更好，更加流畅，更加稳定。

好了，在我们正式编写插件之前，我们还需要先了解一下插件到底在整个游戏的过程中扮演了一个什么样的角色，它是怎么修改我们的游戏的？

我们先从服务器开始说，玩家是如何与服务器产生交互的？

看 ppt 中的思维导图，我们大致将玩家与服务器的交互行为划分为四种，第一种是系统与生命周期行为，包括玩家登入登出，死亡重生，以及切换世界维度等，它们代表玩家在服务器中生存的一些关键阶段。第二种是物理与实体行为，包括玩家移动、攻击、放置方块、破坏方块等，它们概括了玩家在服务器中生存的一些关键行为。第三种是 UI 与物品行为，一些方块和一些实体，包括玩家，都有自己的物品栏，它们需要容纳和处理玩家在生存过程中获得的一些物品，并且处理玩家对这些物品的移动、点击和拖拽。第四种是通讯与逻辑行为，也就是玩家在聊天栏中输入聊天的文本或者执行一些命令，它们概括了玩家主动请求服务器执行一些特殊行为，或者与其它玩家交流的方式。

而世界的变化还不止包含玩家与世界的交互，世界本身也在不断变化的过程当中，实体与实体，方块与环境也每时每刻都在发生着交互，这些内容同样会被服务器所知道，比如说：
一只僵尸看到了村民，并决定追着他
或者说，有一只猪被雷劈了？
还有，悬空的沙子受到重力影响开始往下掉？
或者，漏斗偷偷抽走了箱子里的物品？

这些事件的发生显然都是有迹可循的对吧？从 Bukkit 开始，服务端就会记录下这些事件的发生，并通知到插件，让插件有机会对这些事件进行干预，从而实现我们想要的效果。而这些事件大概可以分为六大类，也就是我们思维导图上展示的这些，也就是 服务器、玩家、世界、容器、方块、实体 这几大类

除此之外，我们还要了解服务器具体是怎么更新世界的，我们为什么能看到世界中的实体在按照正常的速度平滑的运动，而且它们运动的速度似乎与帧率无关？
实际上，Minecraft 中存在 Tick 的概念，也即游戏刻，服务器在每个游戏刻中更新游戏世界。在无意外的情况下，一秒钟之内，游戏世界进行 20 次 tick 更新，也就是 50ms 一个 tick。
在一个 tick 中，服务器会处理所有的事件并更新世界的状态，按照大概这样的顺序：
首先处理玩家行为，然后进行实体和 AI 演算，之后更新世界中的物理环境，最后处理服务器的定时任务，这个具体是什么我们之后会说到。
那么如果我们在一个 tick 中所运行的内容超出了 50ms 会怎么样呢？那自然就会影响到后一个 tick，导致一秒钟之内跑不满 20 个 tick，从玩家视角来看，就是游戏世界变缓慢，怪物的移动开始卡顿，每次攻击或挖掘方块，也要等一会才能生效。

我们之前有说到过好多次 NamespacedKey，我们在这里正式介绍一下它，当你需要添加一些词条，或者注册一些内容时，你需要告诉服务器这是你的插件指定的词条，而不是别的插件指定的，而你注册的内容在插件内部属于哪部分的内容，这样才能完全保证不和别的插件撞车，因此，NamespacedKey 总是由两部分组成，首先是命名空间，也就是你的插件 ID，然后是键名，这个键名是自定义的，只要不重复就可以。
这个 NamespacedKey 相当于一个唯一的身份证，之后如果要注销某个已经注册的东西，比如说配方，那我们也是向服务器提供这个 Key 来自动匹配注销。
